## Reading of the trace

A ballot is written as n * 10 + pid; 11 is (n 1, pid 1).

1. Node 1 calls handle_leader(11). Node 2 promises 11. Node 1 has a majority (itself and node 2), appends v1, and sends AcceptSync to node 2.
2. Node 2 accepts v1. Node 1 receives Accepted and decides index 0 with v1. decided_history is <<v1>>.
3. Node 1 rolls back to its first durable state: promise Ballot::default, empty log. It restarts in Phase::Recover and sends PrepareReq.
4. Node 1 calls handle_leader(11) again. The guard `n > promise` holds, because the rollback removed promise 11. The ballot 11 is now used twice.
5. Node 3 promises 11 with n_accepted 0. Node 1 has a majority (itself and node 3). No promise carries v1, so node 1 appends v2 at index 0.
6. Node 3 accepts v2. Node 1 decides index 0 with v2. Node 2 holds v1 at index 0 with the same ballot 11. S2 fails.

The fault in this trace is a second use of one ballot with a different value. It is the promise of the leader itself that the rollback removes. Model S lets each node call handle_leader with any ballot above its promise. BLE in the source sets n of the new ballot to n of the highest leader ballot it has seen plus one (ballot_leader_election.rs:260-274, check_takeover; update_leader at lines 222-229 takes the maximum of the heartbeat replies). After the rollback, node 1 knows ballot 11 only through a heartbeat reply that carries it. If node 2 is cut off and node 3 never saw ballot 11, BLE computes the same n as before and chooses ballot 11 again. This path is not checked in a model with BLE. Run F6a has succeeded: without recovery, one rollback loses a decided entry.

## Model changes for F6

Spec `model/tla/SequencePaxos.tla`, changes in this block of work:

- Constants `MaxRollback` (number of distinct nodes that roll back, `ASSUME MaxRollback < Cardinality(Nodes)`: a full cluster from a backup is no fault) and `Recovery`.
- `past_durable[k]` holds each earlier durable state (promise, n_accepted, log, decided_idx) of node k. Each step that changes the durable state of k adds the state before the step. The set is emptied when k can no longer roll back.
- `Rollback(i)` chooses one state from `past_durable[i]` and restarts node i with it, in the same way as `Crash(i)` (`Restart(i, d)`, Phase::Recover, accepted_idx = log length).
- With `Recovery = TRUE`, a restart (Crash or Rollback) sends `Recovery` with a fresh nonce (VR Revisited, section 4.3). The node takes part in nothing else until it has f + 1 = Majority answers from other nodes, one from the primary of the highest ballot among the answers. A node in (Leader, Accept) is a primary and sends promise, n_accepted, log and decided_idx; other nodes send only their promise. The node then takes the state of the primary, keeps the higher promise, and continues as a node that restarts (Phase::Recover, PrepareReq).
- The existing config files have `MaxRollback = 0` and `Recovery = FALSE`. With these values no rollback step is enabled, `past_durable` stays empty and a restart sends PrepareReq as before. No earlier run was repeated to check this.

Later change in the same block of work: `Rollback(i)` became `Rollback(R)`, in which all nodes of R roll back in one step, with |R| = MaxRollback, once (run 20261017T074949Z-F6c). `past_durable` is then kept while no rollback has happened. For one node the step is the same: with the bounds of F6b to level 10, both forms gave 5,467,960 states generated and 865,699 distinct states.
