Findings:
1. Plan :294-316 (2.4 item 8) against :252-261 (2.4 item 1). The chosen form drops only the value pages. It does not drop the two LMDB meta pages or the pages on the path. With MDB_REMAP_CHUNKS, the meta pages are the whole of `me_map` (mdb.c:5104-5127), and that map stays mapped. A chunk stays mapped in the env cache after its last transaction ends: mdb_txn_end clears `muse` but does not unmap a shared chunk (mdb.c:3774-3800). `posix_fadvise(POSIX_FADV_DONTNEED)` keeps the pages of a mapped file (bench 163112Z, "after fadvise only: 64/64"). So the drop of the whole file keeps the meta pages and every page in a cached chunk. The bench 195244Z, arm 17, pages out only the value ranges and counts only value pages with mincore. A lost write of an LMDB meta page then passes the read-back. That is the case of review 1, finding 6. Fix: 2.4 item 8 names the meta pages (`madvise(MADV_PAGEOUT)` on `me_mapaddr`, two pages) and the pages on the path, and the bench counts them with mincore. Mark 2.4 items 1 and 6 as the form without chunks.
2. Plan :395-396 and :417-419. HighWaterHolds ran only in the five configs of round 8. They set MaxCrash 0, MaxWipe 0, MaxTimeout 0, MaxLoss 0, MaxDuplicate 0, MaxRollback 0, MaxReconfigure 0, NextConfigNodes {}, MaxForceSingle 0, ClientSessions FALSE, ReadIndex FALSE (model/tla/MC_r_stale_repair.cfg). So no run checks the mark against a recovery after a crash, a wipe, a resend, a second AcceptSync in one ballot (the code accepts a higher session in the same ballot, sequence_paxos.hpp:804-805), a StopSign, a reconfiguration or a forced single node. A false report makes the node copy a peer, so it is a fault of liveness and of the repair path. Fix: run HighWater TRUE with RunningFaults FALSE in the configs of the full model, and one round-8 config with MaxTimeout 1. Until then, 2.3 item 7 says which steps the model checked.
3. Plan :164-171 (2.1 item 5) and model :1634-1640. The model takes the copy from a node that votes and does not recover. Every config has MaxStorageFault 1, so the source never holds an undetected damage. The case "copy from a damaged peer" is not covered, and the plan does not say so. The model also takes the copy in one action from `DurableOf(src)`. The plan does not say how the copy travels: which message, which read transaction on the source, whether the source runs its step check in that transaction, and whether the receiver checks the chain CRC of the copy. It does not say how a node learns that a peer votes and does not recover. Fix: the source runs the step check in the read transaction that gives the copy; the receiver checks the chain CRC before it writes; one config with MaxStorageFault 2 and a damaged source. The protocol is a new design, so the owner decides.
4. Plan :240-245 (2.3 item 7) and :164-171. The plan says "a restart forgets the mark". The repair of 2.1 item 5 is not a restart of the process. The copied state can be below the mark (a peer with a lower promise). The model sets the mark from the copy (`HighWaterUpdate`, `i \in R`, :1278). The plan does not say this. Fix: the repair sets the mark from the copied state. A node of a new configuration starts with a new mark.
5. Plan :155-159 (2.1 item 3), :260 and :301. A read transaction that is kept between steps, the read transactions of the read-back and the write transaction of the step all run in one thread. LMDB says: "A thread can only use one transaction at a time, plus any child transactions" (lmdb.h:98). Parallel read transactions in one thread need MDB_NOTLS (lmdb.h:668-672). The environment opens with no flags (persistent_storage.cpp:403). Every cited bench sets MDB_NOTLS (for example 195244Z, the line `env_flags = MDB_NOTLS | ...`), so the measured form is not the form of the plan. Also, while the kept read transaction holds a chunk, LMDB does not check that chunk again (mdb.c:6872 tests `muse`; muse clears only at the last reference, :3786-3791). Fix: name MDB_NOTLS, and reset the kept read transaction before the read-back.
6. Plan :502-503 (7 item 7) and :299. "The one pointer subtraction: gone" is wrong. 2.4 item 8 calls `madvise` on the page range of a value address. That needs the address rounded down to a page. The bench does it with `reinterpret_cast<std::uintptr_t>` and a mask. The rules say: no pointer arithmetic by hand; a value does not change its type without a check. Fix: put this form to the owner again.
7. Plan :180-182 (2.1 item 8) against :167-171 (2.1 item 5). With page checksums, a read can return MDB_BAD_CHECKSUM (lmdb.h:524, mdb.c:7367). Item 8 throws a type derived from std::system_error for a read error. Item 5 makes a found damage stop the vote and repair from a peer. The plan does not say which path a bad checksum takes. The rule "An error goes to whoever can repair it" needs one answer. This is an error path, so the owner decides. Section 4 has no test for it.
8. Plan :320-322 (2.5 item 1) against :329-332 (2.5 item 4). Item 1 runs a client work in a nested write transaction under the step, and the step commits. Item 4 runs it in a transaction that the follower does not commit. Also open:
   - On which state the follower runs entry k before the decide. If entries below k are accepted and not decided, their effects are not in the committed state. Two nodes then compute two results, their chain CRCs differ (2.3 item 1 covers the result), and the leader counts neither (2.4 item 4).
   - The `state_machine` concept has no transaction (state_machine.hpp:11-14); `node` applies in memory (node.hpp:443) and answers reads from `machine_` (node.hpp:482). The owner, 14:44, says no answer comes from memory. Section 2 does not name this change.
   - Which result goes to the client: the result in the entry, or the result of the run after the decide.
   Fix: delete or rewrite item 1. Put the three points to the owner.

The `promise` message is not in the list of 2.4 item 3. Fix: name it, or state why it is safe.
10. Plan :283-285 (2.4 item 5). A follower whose chain CRC at `d` differs keeps its decided index and votes on. A differing chain CRC is a damage on one of two nodes. The plan does not say whether the follower stops voting or reports. This is an error path, so the owner decides.
11. Plan :226-232 (2.3 item 5). The list of what no local check finds is not complete. The model has no kind for it: `rollback` changes the whole state, `stale_meta` only the meta record (model :1544-1550). The read-back finds it only when the page left the cache, and 7 item 4 accepts that a page can stay. Item 5 also does not name the mark of item 7. 12. Plan :233-239 (2.3 item 6). The model of PeerCheck holds only with no loss and no duplicate (`ASSUME PeerCheck => MaxLoss = 0 /\ MaxDuplicate = 0`, model :2455). Fix: state it, or compare only within one connection that keeps the order.
